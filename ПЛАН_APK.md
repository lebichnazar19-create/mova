# План: пакування «Мова» в Android APK (збірка в GitHub Actions)

Дослідження варіантів пакування, без жодних змін у коді й без встановлення
чогось локально. Мета документа — обрати підхід і чітко зафіксувати, що
доведеться переробити в самій мові незалежно від вибору.

## 0. Що важливо в самій кодовій базі (перевірено читанням коду)

**Хороша новина:** увесь `ядро/*.py` (лексер, парсер, компілятор, VM,
списки, зрізи, дії, підключення файлів) — це **чистий stdlib Python**:
`json`, `shutil`, `subprocess`, `time`, `pathlib`, `dataclasses`. Жодного
`pip`-пакета, тим паче жодного пакета з C-розширеннями (на кшталт numpy чи
Pillow). Це знімає найбільший типовий біль крос-компіляції під Android —
байдуже, який варіант нижче обрати, сам інтерпретатор портується
тривіально: він просто Python-код.

**Погана новина:** пристрій-специфічні модулі **прив'язані саме до
Termux** і не запрацюють у звичайному APK як є, незалежно від варіанту
пакування:

- `ядро/пристрій.py` — **єдине** місце з `subprocess`, і кожна функція
  (`вібруй`, `сповісти`, `скажи`, `тост`, `яскравість`, `гучність`,
  `батарея`, `ліхтар`, `буфер`/`запиши_буфер`, `датчик`, `зніми`, `місце`,
  `відкрий`) викликає окрему **зовнішню утиліту** `termux-*` (наприклад,
  `termux-vibrate`, `termux-notification`). Цих бінарників у звичайному
  APK просто немає — Termux:API тут не «залежність, яку можна докласти»,
  а окрема програма з окремим IPC-протоколом. Реальний (не-симуляційний)
  режим цього файлу **доведеться переписати** під нативний доступ до
  Android API — див. розділ 4, це і є відповідь на «чи можлива вібрація».
- `ядро/розум.py` (`спитай`/`переклади`/`стисни`) — так само `subprocess`
  до `ollama`/`llama-cli`. Поза основним запитом (вібрація), але той самий
  висновок: не запрацює як є в APK. Найпростіший шлях на мобільному —
  тримати ці функції як «недоступні на мобільному» в першій версії, або
  переробити на виклик віддаленого API (окреме рішення, не тема цього
  плану).
- `ядро/екран.py` («живий» режим малювання, `тримай()`) керує **справжнім
  терміналом**: ANSI-послідовності, `termios`/`tty` для сирого режиму
  вводу. На Android немає `tty` в цьому сенсі — це обмеження не залежить
  від варіанту пакування нижче, і чесний варіант — позначити «живий» режим
  недоступним на мобільному (SVG-режим малювання, `ядро/малюнок.py`, і
  режим креслення, `ядро/креслення.py`, не чіпають термінал і працюють
  скрізь, де є файлова система).
- `питай()`/REPL використовують блокуючий `input()` зі stdin. На телефоні
  немає консолі — будь-яка UI-обгортка (в усіх трьох варіантах нижче)
  мусить: (а) виконувати VM в окремому потоці, щоб не заморожувати UI, і
  (б) підмінити `_питай` у `ядро/вм.py` на виклик, що чекає відповіді з
  UI (текстове поле + кнопка «Надіслати») через чергу/`threading.Event`,
  а не читає `stdin`. Це спільна архітектурна вартість для будь-якого
  варіанту — не аргумент на користь одного з них.

Отже порівняння нижче — не про «наскільки складно перенести
інтерпретатор» (однаково легко всюди), а про: (1) скільки треба
Android-специфічного коду навколо нього (UI-оболонка), і (2) як саме
дістатись до вібрації/датчиків/тощо з Python.

## 1. Варіанти

### A. Kivy + Buildozer (+ Plyer для заліза)

**Як працює.** Buildozer — обгортка над `python-for-android`: за одним
текстовим файлом `buildozer.spec` (без Gradle/Kotlin) генерує повний
Android-проєкт, тягне Android SDK/NDK і компілює `.py` файли просто в
APK разом із CPython. UI пишеться на Kivy (Python-фреймворк з власним
рушієм малювання поверх SDL2/OpenGL ES) — для «Мова» це буде мінімальний
екран: текстове поле виводу (`друкуй`), поле вводу (`питай`), кнопка
«Виконати», можливо файловий пікер для вибору `.мова` файлу.

**Збірка в GitHub Actions.** Дуже вторований шлях: готова дія
[`ArtemSBulgakov/buildozer-action`](https://github.com/ArtemSBulgakov/buildozer-action)
(є в GitHub Marketplace) обгортає офіційний Docker-образ Buildozer,
запускається на `ubuntu-latest`, підтримує кешування `.buildozer-global`
(SDK/NDK/platform-tools) між запусками. Мінімальний workflow — кілька
рядків YAML (checkout → крок дії → upload-artifact).

**Заліза (вібрація тощо).** Тут головний козир — бібліотека
[**Plyer**](https://github.com/kivy/plyer) (той самий проєкт Kivy),
яка вже має Android-реалізацію для більшості потрібного:

| Функція `ядро/пристрій.py` | Plyer facade | Готовність |
|---|---|---|
| `вібруй` | `plyer.vibrator` | є, підтверджено (вібрація на Android, зокрема патчі під API 26+) |
| `сповісти` | `plyer.notification` | є |
| `батарея` | `plyer.battery` | є |
| `ліхтар` | `plyer.flash` | є |
| `місце` | `plyer.gps` | є |
| `зніми` | `plyer.camera` | є |
| `датчик` | `plyer.accelerometer`/`gyroscope`/`light`/`proximity`/… | є, але **окремий facade на кожен тип** — на відміну від `termux-sensor "назва"`, доведеться зробити словник «назва → facade» в `ядро/пристрій.py` |
| `буфер`/`запиши_буфер` | вбудований `kivy.core.clipboard.Clipboard` (не Plyer, ще простіше) | є |
| `яскравість` | часткова підтримка в новіших Plyer, варто перевірити на місці | потребує перевірки |
| `гучність`, `тост`, `скажи`, `відкрий` | немає готового facade | пишеться напряму через `pyjnius` (`from jnius import autoclass`) — Kivy вже тягне `pyjnius` як залежність, тож без нових бібліотек; це типові, добре задокументовані в спільноті Kivy рецепти (Toast/AudioManager/Intent.ACTION_VIEW за кілька рядків) |

Тобто **більшість** заліза — рядок-два виклику готової Python-функції;
решта (гучність/тост/TTS/відкрий) — невеликі, але власноруч написані
`pyjnius`-обгортки. Увесь цей код лишається **чистим Python**, без
Kotlin/Java файлів і без Android Studio.

**Розмір APK.** За практикою спільноти — «hello world» на Kivy/Buildozer
(одна ABI) типово **~12.5–30 МБ** залежно від конфігурації (мінімальний
Python + SDL2 + Kivy вже важать чимало самі по собі, ще до логіки
програми). Для «Мова» це базова стеля — сама мова додасть мало (чистий
stdlib), але Kivy як фреймворк несе накладні витрати графічного рушія,
які для консольного за духом інтерпретатора трохи надлишкові (переплата
за OpenGL-стек заради текстового виводу) — не блокер, просто нюанс.

**Складність і ризики.** Buildozer/`python-for-android` — проєкт з
довгою історією (роки використання, багато прикладів), але з періодами
повільнішої підтримки; перша збірка типово повільна (тягне й компілює
NDK-тулчейн), нові версії Android API інколи вимагають оновлення
рецептів. У CI це помітно менше болить, бо `buildozer-action` кешує
важкі каталоги між запусками.

### B. Chaquopy

**Як працює.** Chaquopy — Gradle-плагін для Android Studio, що вбудовує
повноцінний CPython у звичайний Android-застосунок (Kotlin/Java UI +
Python-логіка). Java/Kotlin і Python викликають одне одного напряму:
`Python.getInstance().getModule("вм").callAttr(...)` з боку Kotlin, або
`from java import ...` / прямий доступ до Android SDK-класів з боку
Python. Для «Мова» це виглядало б так: мінімальний Android-проєкт з
однією `Activity` (текстовий вивід + поле вводу + кнопка), яка викликає
`мова.py`/`ядро.вм` як бібліотеку.

**Важливе оновлення (перевірено пошуком, а не з пам'яті — ліцензія
Chaquopy історично була платною для закритого коду):** з версії **12.0.1
Chaquopy повністю безкоштовний і відкритий (MIT), за підтримки Anaconda**
— увесь код на GitHub, жодних обмежень на комерційне/закрите
використання. Це знімає раніше актуальний пункт «треба публікувати
репозиторій, щоб не платити» — тепер він не стоїть узагалі, для жодного
типу проєкту.
([chaquo.com/chaquopy/chaquopy-is-now-open-source](https://chaquo.com/chaquopy/chaquopy-is-now-open-source/),
[chaquo.com/chaquopy/free-license](https://chaquo.com/chaquopy/free-license/))

**Збірка в GitHub Actions.** Це звичайна Android Gradle-збірка —
найбільш вторований з усіх трьох шлях у світі CI (`setup-java` +
Android SDK cmdline-tools + `./gradlew assembleRelease`), тисячі готових
прикладів поза межами Python-екосистеми. Менше специфічних «сюрпризів»,
ніж у крос-компіляції NDK-тулчейну Buildozer.

**Заліза (вібрація тощо).** Chaquopy дає прямий доступ до будь-якого
Android/Java класу з Python (той самий принцип, що й `pyjnius` — рефлексія
через JNI), тобто вібрація/`NotificationManager`/`AudioManager`/тощо
технічно **доступні** — офіційно підтверджено можливість «Calling Java
from Python». Але, на відміну від варіанту A, **готової бібліотеки
рівня Plyer під Chaquopy немає** — кожен із ~12 викликів
`ядро/пристрій.py` доведеться самостійно написати як звернення до
відповідного Android System Service (`Context.getSystemService(...)`),
або винести в тонкий Kotlin-хелпер і викликати його з Python. Обсяг
роботи — той самий порядок, що й «ручні» рецепти для
гучності/тосту/TTS у варіанті A, але тут **усі 12**, а не 3-4, бо немає
Plyer, що закриває решту з коробки.

**Розмір APK.** Точних вимірювань для мінімального застосунку в
пошуку не знайдено (демо-застосунок Chaquopy на Google Play важить
~46-52 МБ, але це багатофункціональне демо з REPL і кількома
активностями — не орієнтир для мінімального «Мова»-застосунку). За
непрямими даними з обговорень у репозиторії Chaquopy базові накладні
витрати одного ABI без важких бібліотек — порядку **15-25 МБ**;
драматичне роздування (сотні МБ) трапляється лише з важкими
бібліотеками на кшталт TensorFlow, чого в «Мова» немає. **Це оцінка,
не заміряне число — перед остаточним рішенням варто зробити порожній
`chaquopy-hello`-проєкт і подивитись реальний розмір.**

**Складність і ризики.** Потребує **одного** мінімального Android
Studio/Gradle проєкту в репозиторії (навіть якщо збирається лише в CI):
`build.gradle`, `AndroidManifest.xml`, один `Activity`-файл, базовий
`res/layout`. Це не Kotlin-важка робота (можна тримати логіку майже
всю в Python), але це **новий тип файлів** у проєкті, якого зараз немає
взагалі (проєкт — чистий Python). Офіційно підтримується компанією
(Anaconda) — нижчий ризик занепаду проєкту, ніж у волонтерського
`python-for-android`.

### C. BeeWare (Briefcase + Toga)

**Ключовий факт, перевірений пошуком, а не очікуваний заздалегідь:**
Android-бекенд Toga **повністю побудований на Chaquopy** — це
підтверджено і документацією Toga, і обговореннями в репозиторії
`beeware/toga` («The Android backend for Toga is entirely written using
Chaquopy», Toga перейшов на Chaquopy кілька років тому).
([toga.beeware.org/.../android](https://toga.beeware.org/en/latest/reference/platforms/android/),
[github.com/beeware/toga discussion #3743](https://github.com/beeware/toga/discussions/3743))

Тобто BeeWare на Android — це **не третя незалежна технологія**, а
«Chaquopy + віджети Toga + інструментарій Briefcase (генерація
Gradle-проєкту, пакування)» зверху. Практичний висновок:

- Успадковує від Chaquopy те саме (тепер безкоштовне) ядро — жодного
  окремого ліцензійного питання.
- **Не** дає нічого на кшталт Plyer — доступ до заліза все одно йде через
  той самий Chaquopy Java-міст, тобто той самий обсяг ручної роботи, що
  й у варіанті B, плюс шар Toga/Briefcase зверху.
- Android-бекенд BeeWare молодший і менш обкатаний за роки, ніж або
  Kivy/Buildozer (найдовша історія на Android), або сам Chaquopy напряму;
  спільнота й документація саме під Android помітно менші.
- Головна цінність BeeWare — «один UI-код на desktop+mobile» (Toga-віджети
  виглядають нативно на кожній платформі). Це нічого не додає до задачі
  «спакувати інтерпретатор мови у APK з іконкою», якщо немає окремої
  потреби в такому крос-платформному UI.

**Висновок по варіанту C:** не розглядається як окремий кандидат —
фактично підмножина варіанту B з додатковим шаром складності без
компенсуючої переваги для цієї задачі.

### Відкинуті одразу (коротко, без глибокого аналізу)

- **Запакувати як є під Termux** (наприклад, ярлик Termux:Widget на
  скрипт) — не дає окремого інстальованого APK з власною іконкою й
  ідентичністю застосунку, а лише ярлик усередині вже встановленого
  Termux; не відповідає запиту.
- **`python-for-android` напряму, без Buildozer** — Buildozer і є
  стандартна зручна обгортка над ним; іти в обхід означає більше ручної
  роботи без жодної вигоди.
- **Qt for Python (PySide6) для Android** — підтримка Android у
  PySide6 історично експериментальна/менш стабільна, набагато важчий
  фреймворк, значно менше готових CI-рецептів під GitHub Actions — не
  вартий розгляду поруч із трьома вище.

## 3. Рекомендація

**Основний вибір: A — Kivy + Buildozer + Plyer.**

Чому саме цей, а не Chaquopy (який тепер, після зняття ліцензійного
питання, теж цілком життєздатний і в дечому технічно охайніший варіант):

1. **Увесь проєкт «Мова» зараз — чистий Python** (навіть інструментарій
   довкола: тести, CLI, README — усе Python/Markdown, жодного
   Kotlin/Gradle файлу). Buildozer продовжує цю лінію: `buildozer.spec`
   — текстовий конфіг, не Android-проєкт, який треба підтримувати
   окремо. Chaquopy вимагає завести (і надалі підтримувати) справжній
   Android Studio/Gradle-скелет у репозиторії — новий тип артефакту й
   нова, раніше не потрібна експертиза.
2. **Plyer закриває більшість функцій `ядро/пристрій.py` без жодного
   рядка Java/Kotlin** — вібрація, сповіщення, батарея, ліхтарик, GPS,
   камера, датчики. Це саме про «чи можливо керувати пристроєм», що
   явно турбувало в запиті: так, і здебільшого без нової мови/технології,
   лише заміна `subprocess`-виклику на виклик `plyer.<модуль>`.
3. Збірка повністю в GitHub Actions — так само реалістична, як і в
   Chaquopy (`buildozer-action` проти `gradlew`); жоден з варіантів не
   вимагає нічого локального на телефоні, що й було умовою.

Це не означає, що Chaquopy — гірший вибір. Якщо згодом виявиться, що
Plyer чогось не тягне достатньо надійно (є відкриті issue про
нестабільність вібрації на деяких версіях Android — варто перевірити на
цільових пристроях), Chaquopy — цілком розумний план Б: тепер безкоштовний,
офіційно підтримуваний, з найбільш «звичайним» CI-шляхом. Перемикання
недешеве (інша структура проєкту), тому варто зважити зараз, а не після
першої спроби.

## 4. Що доведеться зробити в коді (спільне для варіанту A; коли дійде
до реалізації — окремим кроком, не зараз)

1. `ядро/пристрій.py`: замінити реалізацію кожної функції (не
   сигнатуру!) — з `subprocess`-виклику `termux-*` на відповідний
   Plyer/`pyjnius`-виклик, під прапорцем платформи (лишити Termux-шлях
   для розробки/тестів на комп'ютері, додати Android-шлях, який активний
   лише коли `kivy.utils.platform == "android"`). Симуляційний режим
   (`--без-пристрою`) не чіпається — тести на комп'ютері й далі йдуть
   через нього.
2. `ядро/вм.py`: `_питай` — замінити блокуючий `input()` на очікування
   значення з черги, яку наповнює UI-потік; VM запускати в окремому
   потоці від UI.
3. Мінімальний Kivy-екран: поле виводу (прив'язати до `друкуй`), поле
   вводу + кнопка (прив'язати до нового `_питай`), кнопка «Виконати
   файл» (файловий пікер або вбудований приклад).
4. `buildozer.spec`: `requirements = python3,kivy,plyer,pyjnius`,
   `android.permissions` — перелік дозволів під кожну функцію, що
   лишається (VIBRATE, CAMERA, ACCESS_FINE_LOCATION, тощо — лише ті,
   що реально використовуються).
5. Іконка застосунку: `icon.filename` у `buildozer.spec` (просто PNG-файл
   у репозиторії).
6. `.github/workflows/apk.yml`: checkout → `ArtemSBulgakov/buildozer-action`
   → upload-artifact (готовий APK як артефакт запуску; публікація в Play
   Store чи деінде — окреме питання, не в межах цього плану).
7. `ядро/екран.py` (живий термінальний режим) і `ядро/розум.py`
   (`спитай`/`переклади`/`стисни`) — задокументувати як «недоступні на
   мобільному в першій версії», а не намагатись портувати одразу.

## 5. Що варто перевірити емпірично перед остаточним рішенням

- Реальний розмір мінімального Buildozer-APK саме з `plyer`+`pyjnius`
  доданими як залежності (цифри вище — з чужих проєктів, не з «Мова»).
- Чи справді стабільно спрацьовує `plyer.vibrator` на цільових версіях
  Android (в issue-трекері Plyer є повідомлення про проблеми на певних
  API-рівнях, нібито вже пофіксені — варто перевірити на пристрої, який
  реально буде використовуватись).
- Чи потрібен `яскравість()` як точна відповідність термукс-версії —
  підтримка яскравості екрана в Plyer новіша й менш обкатана за решту.
